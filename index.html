About

I'm a final-year Computer Science student at Lovely Professional University who likes building the parts of software people rarely see: APIs, data models, deployments and the monitoring around them.

My recent projects sit where backend meets infrastructure and AI: an incident-response copilot for Kubernetes, a canary release platform that rolls back bad deploys on its own, and a full-stack reading app with real-time chat and payments.

I care most about what happens when things go wrong, like a duplicate webhook, a replayed token or a crashed worker. That is usually where the interesting engineering is.

    Engineering approach

    1. Build

      APIs and interfaces with a contract.

      Validate at the boundary, keep one error format, document the API. Library Tracker validates every request with Zod and publishes OpenAPI docs. CanaryShield's admin API returns a single error shape.

    2. Operate

      Systems you can see into.

      Metrics, logs and traces come first. OpsPilot's demo cluster ships Prometheus, Loki, Tempo and an OpenTelemetry Collector as Kustomize manifests, and every service exports its own metrics.

    3. Improve

      Correct behaviour under failure.

      Assume duplicates, restarts and missing data. Payment webhooks are idempotent, the telemetry queue survives a worker crash, and the CanaryShield guardian skips a check rather than act on missing data.

    4. Explore

      AI that shows its evidence.

      Retrieval and tool use are only useful when the answer can be checked. OpsPilot's agent cites the query behind every claim and waits for a person before it changes anything.
